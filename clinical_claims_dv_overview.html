Tag-based masking

Three masking policies are bound once to the SENSITIVITY tag, one per data type: text becomes ***MASKED***, numbers become NULL, and dates are cut to the year. All three share one function, UNMASK_PHI(), which lets PHI_READER (and ACCOUNTADMIN) see clear values.

Hash keys are BINARY, and the system metric functions have no BINARY versions, so hash keys are covered by dbt tests instead. Column-level FRESHNESS has no TIMESTAMP_NTZ version, so the hubs use the table-level FRESHNESS(). The macro skips metric functions that are already attached, which matters because the mart tables are recreated on every run.

What the vault adds here, stated plainly

ClaimFinding on this data
Removes duplicatesNot needed The source has 0 duplicate and 0 null business keys. The vault prevents duplicates on reload, because hubs and links only insert keys they haven't seen.
Improves data qualitySource already clean 0 orphan patient, provider and payer keys on encounters and claims; 2 claims with no encounter. The gains are history (satellites), an audit trail (load time and record source) and PII isolation.
Faster joins via hash keysNot here The source keys are single numbers, and joining on a 16-byte binary hash is no faster. Hash keys pay off for multi-column or text keys, combining sources, and parallel loading.

10Staging and the sampling fix

The first build capped each table at 100,000 rows independently. Only 4,746 of 52,989 patients referenced by the sampled encounters existed in hub_patient, so business vault joins mostly didn't match.

The fix is dev_sample(): keep every row where MOD(PATIENT_ID, 50) = 0. Providers, organizations and payers are loaded in full.

14Known gaps and next phase

Open items
  • The 36 staging views have no descriptions. Raw vault, business vault, marts and clean room are documented.
  • The raw vault ← staging hop isn't in Horizon lineage yet (see section 13).
  • The point-in-time table uses AutomateDV's deprecated pit() macro. It could be rewritten in plain SQL.
  • The clean room is the single-account version. A real two-party clean room needs the Data Clean Rooms app and a partner account.
  • Everything is built on a 2% patient sample. A full load needs a larger warehouse.

Next phase: data quality and observability. Build on the metric functions already attached: add expectations (thresholds), quality notifications, health scoring and trend dashboards, and data quality monitoring on the agent itself.
